# Ship With Proof

Run the whole chain in this session. Creating the PR is an intermediate milestone, not completion. The gates form a loop, not a line: a late behavioral fix invalidates the evidence for the code it touches, so re-run the gate that covered it. A caller may add requirements to any step but may not remove a gate. Report a gate you cannot satisfy instead of skipping it. Do not merge.

For a [`telemetry-hunt`](../telemetry-hunt/SKILL.md) handoff, implement on a branch and reproduce the failure, then prove the fix with scoped tests and the affected local end-to-end flow before opening any PR. Measure the changed path before and after under identical conditions for a performance fix. Stop without opening a PR if that proof fails. Then complete every gate below on the proven head, repeating proof when a later edit changes behavior.

## Needed from the caller

- The task, or an existing PR URL or number if the code is already written.
- The user-facing flow the proof must exercise, if it is not obvious from the diff.
- Any PR content the caller requires beyond this skill, such as a dedupe marker line, an evidence section, or an artifact.

Ask only when a missing choice affects the work: the intended behavior, a non-obvious proof flow, the required reviewer, or an external destination.

## Resolve scope and dependencies

Use the current or requested repository and its `AGENTS.md`, README, PR template, CI workflow, testing conventions, and verification commands. Do not assume a repository name, package manager, default branch, reviewer, review bot, messaging channel, or browser host. A layer the repository has no harness for is `n/a (<reason>)`. With no user-facing surface, "the recording" below is an end-to-end run plus its logs (for docs or skill text, the repository's validation run and its output). A repository with no end-to-end harness reports the e2e layer as `n/a (<reason>)`, and its recording is a manual invocation of the changed path (the script, job, or config load) plus its logs. "Base" means the PR's base ref (the default branch before the PR exists). Every other gate still applies.

Skills this workflow uses: [`git-commit`](../git-commit/SKILL.md), [`gh-stack`](../gh-stack/SKILL.md), [`prose-pass`](../prose-pass/SKILL.md), [`show-me`](../show-me/SKILL.md), [`principle-test-behavior-not-implementation`](../principle-test-behavior-not-implementation/SKILL.md), [`statechart`](../statechart/SKILL.md), [`thermo-nuclear-code-quality-review`](../thermo-nuclear-code-quality-review/SKILL.md) with [`thermo-fix-loop`](../thermo-fix-loop/SKILL.md), [`code-diagram-html`](../code-diagram-html/SKILL.md), [`viz`](../viz/SKILL.md), [`create-pr`](../create-pr/SKILL.md), [`before-after-ss`](../before-after-ss/SKILL.md), [`sol-loop`](../sol-loop/SKILL.md) (or [`sol-loop-devin`](../sol-loop-devin/SKILL.md) in Devin), [`equivalence-review`](../equivalence-review/SKILL.md), [`review-loop`](../review-loop/SKILL.md), and [`merge-risk`](../merge-risk/SKILL.md), plus the repository's own unit, integration, e2e, and review-thread skills when it has them. Load each when its step begins. Name a missing skill rather than pretending it ran, and continue independent work meanwhile.

## Procedure

1. Implement the change and open the PR. Search for an existing PR covering the same change first and reuse it. When the caller asked for a stack, or the change builds on an open PR and the caller said to stack it, open it as a GitHub-native stack layer with `gh-stack` (`gh stack link`/`gh stack add`), never as a PR with a hand-set base. Open each PR as the requester, since a PR's author cannot change later: `gh stack submit` opens missing PRs as the `gh` CLI identity, so run it only once every layer already has a PR. Check each new PR's author right after creating it; close a bot-authored PR and reopen it as the requester, with a comment on the old one pointing at the new one. Follow the repository's agent guidance, run its required checks, keep the diff minimal, preserve unrelated work, response contracts, and error precedence, and keep each stack layer independently reviewable. Title it with a conventional prefix and include everything the caller requires. Run `prose-pass` in embedded mode over the title and body before posting, and over every PR comment, commit message, and review reply this skill posts later; a doc or user-facing string the diff adds or changes gets the same pass before it is committed. Add a standalone `## Show me` section, separate from Summary and from `## Visualization`: apply `show-me` inline in GitHub-renderable markdown (a `diff` of the call tree, pseudocode, component tree, file tree, or a Mermaid diagram), one or two blocks with real symbol and file names. If the repository gates preview deployments on a PR label, add it once the PR is out of draft and put the preview URL in the body once it lands.
2. Prove every feature at every applicable layer. List each behavior the diff adds or changes, then give each one its own proof at each layer that applies. A behavior counts as proven only when a changed-behavior assertion fails on base and passes on the head, plus an unchanged-input case that passes on both, showing nothing else moved. Run identical test code on both sides: in a worktree at base, check out only the head's test files (`git checkout <head> -- <test paths>`) and run them there. A missing file, import error, or setup crash does not count as a base failure. Only a failing assertion does. For a change with no executable behavior, state why each layer is inapplicable rather than inventing a test.
   - **Unit**: the defect or new case, its edge and error cases, and equivalence on unchanged inputs. For a state machine (a `kind` union with a `transition(state, event)`, or a reducer standing in for it; `transition` below means that entry point whatever its name), the unit row is a table test over every (state, event) pair, rejected pairs included, plus a fast-check property test (`fc.assert(fc.property(...), { seed: 1337, numRuns: 100 })`, or the language's property-testing equivalent with a pinned seed) that drives random event sequences through the real `transition` and asserts the rules the change promises. When `transition` exists on both branches, both tests run base and head like every other unit proof; when the head's tests import a runtime value base lacks (a new event constructor or enum member, which fails base at import rather than at an assertion), split them so the unchanged-input cases import nothing new and run on both, and only the cases that need the new value are head-only, recorded as such in the row. When `transition` is new on head (a flag-to-union migration), both tests are head-only coverage, recorded as such, and the base-fails, head-passes assertion goes through the public boundary both branches share (the hook, component, or route that owned the flags).
   - **Integration**: the behavior crossing its real boundaries, such as route to handler to database, a service binding, a Durable Object, or a queue. Use the real local dependency, not a mock of it.
   - **E2E**: a committed automated test that drives the user-facing flow through the repository's e2e harness. Add it in addition to the recording in step 4, never in its place.
     When the change adds or alters a high-risk state machine, also model-check it with `statechart`: a TLA+ spec of the new behavior with the rules the change promises as INVARIANTs. High-risk means the machine governs money (credits, billing, caps, refunds), auth (keys, entitlements, capabilities), a request lifecycle, concurrent or retried work (queues, workflows, locks), or data deletion and retention; a presentation-only lifecycle (modal, form, fetch phases, wizard steps) that governs none of those is not, and stops at the table test and the property test. Domain wins over surface: a payment form or a deletion wizard is high-risk. The model is not a proof layer and enters no proof-matrix row, because it checks the spec, not either branch. A path that breaks a rule in the model is replayed against the real code first: against `transition` for a single-actor path, and against the concurrent boundary (the Durable Object, queue consumer, or workflow) for an interleaving, since a pure `transition` replay cannot show a race. A path neither replay reproduces is a spec defect, so correct the model before touching the implementation. A path the code reproduces, or a property-test counterexample, is a code defect: a single-actor path becomes a table-test row; an interleaving becomes a deterministic integration test that schedules the actors in the counterexample order through the real boundary and sits in the Integration row. Fix the code and re-run the model and the new test before step 3. When the defect is the behavior the change set out to fix, that row is the base-fails, head-passes assertion. When head alone introduced it, the row is regression coverage: it passes on the fixed head, and the pass-on-both check runs where base can run it, on the row itself when `transition` exists on base, otherwise through the shared public boundary. The property test and the model check the same single-actor rules, so such a rule added to one is added to the other; an interleaving rule lives in the model and the Integration test. Keep `chart.mmd` and the rules it checked for step 6. A passing model above the `statechart` chart budget writes no `chart.mmd`; reduce the model per that skill until it does, and if reducing it would drop a relevant case, keep the TLC report for step 6's fallback.
     Strongly prefer the local stack (local databases, local workers, the repository's documented dev environment) over mocks, fakes, or remote environments. Proof against production or a preview counts only for a surface that cannot run locally, and the PR has to say why. Every test you add or change follows `principle-test-behavior-not-implementation`. A layer that does not apply to a behavior is recorded as `n/a (<reason>)`, never left blank or skipped silently. Never edit or weaken an existing test so the new behavior passes; a test that must change is a behavior change to explain in the PR, with its regression coverage preserved. Record the result in the PR body as `## Proof matrix`, one row per behavior and a column per layer. Each cell names the test file and test name, the command that ran it, and the base assertion failure (expected vs. received) next to the head pass.
3. Run the thermo fix loop until it is clean. Run `thermo-nuclear-code-quality-review` over the entire scoped diff and relevant surrounding code (`thermo-fix-loop` drives the repetition), fix every actionable finding, run verification, push, and review the new head in full again; a pass is never limited to checking earlier findings. A finding is actionable when it names a structural problem the diff introduced and the fix stays inside the diff's scope. Refute others in writing on the PR, and explicitly defer anything that would grow the PR beyond this change, cross an architectural layer, or require product judgment; a deferred finding never counts as fixed. Stop after the fourth round even if findings remain, document them, and report the gate as incomplete; this cap overrides the loop skill's unbounded repetition. Do not create a separate goal unless the user or host authorizes one. Record the loop under `## Thermo-nuclear fix loop`, one block per round with the reviewed head, findings, fixes or dispositions, and verification, keeping the last round's empty result visible.
4. Record end-to-end proof as soon as thermo is clean. Do not wait on reviewers, CI, or any other asynchronous gate. Use the repository's e2e skill or test environment and the available recording tools, and cover both halves: the new behavior working, and at least one adjacent pre-existing flow the diff could plausibly break, still working. Annotate with `test_start` and `assertion` markers when supported, or equivalent visible labels and a timestamped test log. Record the tested commit and exact scenario. Keep credentials and private user data out of recordings and logs. For an API-only, CLI, or backend change, an e2e run with captured request/response or structured log evidence replaces the video; say what it proves and why video does not apply. If the needed runtime, credentials, or capture tool is unavailable, report the gate as blocked; screenshots alone do not establish an interaction sequence.
5. Re-record on any failure. A recording showing a failed assertion, an error, a stuck state, or a broken layout is a finding, not a deliverable. Fix the code, push, and record again from scratch. If the fix is substantive, return to step 3.
6. Visualize the change. Build one self-contained artifact named `<change-slug>-<date>.html` with `code-diagram-html` that makes the defect and the fix, or the new behavior and affected flow, legible without reading the diff. Follow `show-me` for what to show and `code-diagram-html` and `viz` for how it looks; start from that skill's neutral defaults, never by copying an earlier artifact or another skill's HTML. Real labels and real numbers, readable on desktop and mobile. Pick the spine that fits the change (sequence, flow, decision tree, before/after, or state machine), not before/after by default: a change that replaces lifecycle flags or a status field with a discriminated union, reducer, or transition function gets the state-machine spine, two state graphs side by side with states as nodes, transitions as labeled edges, and the old impossible flag combinations struck out. In `## Show me`, the new machine goes in as a `mermaid` `stateDiagram-v2` block so GitHub renders it inline: for a high-risk machine the step 2 `chart.mmd` followed by the rules it checked, or, when the model stayed over the chart budget, a diagram drawn from the table test with a `note` reading `unchecked: drawn from the table test`, followed by the invariants the TLC report checked; for any other machine a diagram drawn from the step 2 table test, one arrow per accepted (state, event) pair, followed by the rules the property test asserts. Either way a `note` names the combinations that became unrepresentable and the transitions that became no-ops. The old machine lives only in the artifact. The artifact holds that spine, the measured numbers with workload and iteration count when the change is performance-shaped, the decisive tests and thermo rounds, and the evidence links the PR carries. Every number comes from this run's captured output; never invent one to fill a chart. Inline CSS and inline SVG only, no network assets, no build step, one page. Deliver it through `create-pr`: rasterize it at 2x, split into as many PNGs as keep every section legible, embed them under `## Visualization` (directly after `## Show me` and before `## Before / after`) when an authorized reviewer-accessible host is available, and link the downloadable HTML when available. Never invent URLs, expose private artifacts publicly, or assume a local Markdown path uploads a file. When rendering or hosting is unavailable, keep the local artifact, keep `## Show me` complete on its own, and report the limitation; that does not block the body update or this workflow. For a change too small to benefit from an HTML artifact, state the reason in the PR. A browser is optional for checking the explainer's raster; this does not relax browser use needed to test the actual flow.
7. For any change with a user-facing surface, run `before-after-ss`. It captures the same surface on base and on the branch at the same viewport and state, in both light and dark mode, highlights the changed element in both shots, and writes a one-line what-to-look-for caption per row. Put its output in the PR body as `## Before / after`, below `## Visualization`, a light and a dark row per changed surface, with unrenderable surfaces or themes listed as `not measured (<reason>)`. The images are rendered app or Storybook pixels, never the visualization artifact. Skip this step only for a change with no user-facing surface, and say so in the report.
8. Post the recording (or equivalent backend evidence) and its key screenshots as one PR comment with the actual uploaded URLs embedded, stating which flow each item proves. Send the caller the PR link and evidence now, before review is requested.
9. Run the Sol correctness loop (`sol-loop`, or `sol-loop-devin` in Devin) on the final diff, on every PR. Sol is an independent-model correctness review, so it runs after thermo has settled the structure, after the evidence has gone to the caller, and before review is requested. The Sol reviewer reads only pushed commits, so push each agreed fix before the next round and name the new head in it; continue the same Sol reviewer until it returns `APPROVE` on the current head or a round with only nits (declined nits recorded in the ledger). A behavior-changing push after that approval needs another round. If the round budget runs out or an item stays disputed, stop and ask the caller per that skill, and change behavior only after their decision. A fix that changes behavior re-runs the affected proof and recording, and the new recording replaces the step 8 comment and caller message. Record the ledger and the reviewer's model and session link under `## Sol review loop`.
10. For a refactor, move, or migration (any PR that claims to be purely mechanical), run `equivalence-review` on the diff once Sol is clean. Every unintended behavior change it finds is a finding: fix it and go back through the gates it touches. Move on only at `✅ Pass`: prove every `⚠️` unproven row. If a row cannot be proved, stop the gates there and go straight to step 15, reporting each unproven row as an open blocker with the evidence it needs, never as done. Put its verdict and evidence in a `## Equivalence` section, and rerun it whenever the head changes after it passed: a CI or review fix, or a rebase or merge from base.
11. Request the repository's required review with `review-loop` as soon as steps 1–10 are complete: the reviewer or review bot the user named or the repository's rules require, through its normal mechanism, one request from this session. Send it before waiting for CI: pending, failing, or infrastructure-blocked CI must not delay it. Never treat one reviewer's approval as satisfying all branch rules; if approval is required but no reviewer can be identified, ask while continuing CI work. Posting to Slack or another external channel requires explicit authorization for that destination. Do not hand review to a separate babysitter session; it pushes to the branch behind you.
12. Get CI green and every review thread resolved while review runs. Inspect checks and failing job logs with the available GitHub tools, fix failures the change caused, and report unrelated infrastructure failures accurately. Use the repository's review-thread skill when it has one. If CI stays blocked, continue the review loop and report the CI blocker separately; green CI is a merge-readiness gate, not a prerequisite for requesting review.
13. Handle review comments yourself as they arrive. Fix or refute each one, push scoped commits, rerun affected checks, reply on the thread, resolve it only when addressed and repository conventions permit, and re-request review in the same conversation only when needed. Repeat until approved. Do not re-request after approval. A rebase or merge from base does not need re-approval unless the repository's rules dismiss approvals on push. If a reviewer is unavailable, authorization is missing, or an external service stays blocked, preserve the state and report the exact outstanding gate rather than waiting or retrying indefinitely. Do not set up a recurring monitor unless asked.
14. Run `merge-risk` on the final head once review is approved, CI is green, and every thread is resolved. Append its output verbatim to the end of the PR body as `## Merge risk`, replacing any earlier one. It keeps merge-risk's format, so `prose-pass` does not rewrite it. A push after this step re-runs it.
15. Refresh CI and review status after every push. Report the PR link, final head, approval and CI states, thermo result, Sol verdict, equivalence verdict where it applies, merge-risk level, artifact and image links with any rendering or hosting limitation or small-change exception, the recording or equivalent evidence URL, and anything not tested and why. Evidence may come from an earlier commit only when its covered behavior still matches the final head; say so rather than claiming it was recorded on the final commit. When a caller owns the final report, hand it these facts instead of ending the session.

## Done means

- The repository's required approvals are current, required CI is green, and no review thread is unresolved.
- A refactor, move, or migration PR carries a `## Equivalence` section with a `✅ Pass` verdict from `equivalence-review`, run on the final head.
- The PR body ends with a `## Merge risk` section from `merge-risk`, run on the final head after every review gate.
- The PR body has a `## Proof matrix` with every changed behavior covered at unit, integration, and e2e level, or marked `n/a (<reason>)` per layer. Each applicable layer ran on the local stack unless the PR explains why it could not. For every applicable layer, a changed-behavior assertion failed on base with the head's test code and passed on head, while unchanged-input cases passed on both.
- The final thermo pass produced no unaddressed finding, or the fourth round is documented as the stopping point and reported as incomplete.
- The PR has a `## Sol review loop` section ending in `APPROVE` or a nit-only round, with no open blocker or should finding, or the caller's recorded decision on each item left open at budget end.
- The recording or equivalent evidence shows both the new behavior and a non-regressed adjacent flow, made against a head whose covered behavior matches the final head, and every assertion passed.
- The PR carries the recording and the report carries the PR link and recording URL.
- The PR body has a standalone `## Show me` section with at least one block that renders on GitHub.
- Every PR title, body, comment, commit message, and review reply this session posted went through `prose-pass`, and so did every doc or user-facing string the diff adds or changes.
- For a UI change, the PR body has a `## Before / after` section with every changed surface shown as a highlighted pair in light and dark mode or listed as not measured.
- The visual artifact exists, and when rendering and hosting were available its PNGs sit in `## Visualization` above `## Before / after` with the HTML linked; otherwise the report names the limitation or the small-change reason.
- Every number in the artifact appears in the run's captured output.

## Forbidden

- Do not start a child session for review or hand the PR to a babysitter, except the one Sol reviewer step 9 runs.
- Do not withhold the review request because CI is pending, failing, or infrastructure-blocked.
- Do not modify tests to make them pass.
- Do not treat the recording as a substitute for a committed e2e test, or a mock as a substitute for a local dependency that can run.
- Do not use `<details>` or any other collapsible element in the PR body, comments, or chat messages.
- Do not merge the PR.
- Do not open a PR as a bot or CLI identity, including through `gh stack submit`; the author must be the requester.
- Do not commit the artifact, its PNGs, recordings, or the before/after PNGs to the repository.
- Do not put a number, chart, or label in the artifact that the run did not measure.
- Do not change application source or seed data only to make a screenshot easier.
