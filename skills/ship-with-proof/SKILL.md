# Ship With Proof

Run every gate in this session. A behavioral fix invalidates the evidence for the code it touches; re-run the gates that covered it. A caller may add requirements, never remove a gate. Report a gate you can't satisfy; never skip it.

## Completion checklist

Keep one checklist of the gates below in the PR body, with status, evidence links and verified commit. Reload it on resume and before CI repair; preserve unfinished gates when narrowing tasks.

## Needed from the caller

- The task, or an existing PR URL or number.
- The user-facing flow the video must exercise, if the diff doesn't make it obvious.
- Any extra PR content required (dedupe marker line, evidence section, artifact).

## Procedure

Commands, paths, test skills, the reviewer, and the review channel come from the repo's `AGENTS.md`, README, PR template, and CI; assume no repository name, package manager, default branch, review bot, or chat channel. `origin/main` means the PR's base ref. A layer with no harness is `n/a (<reason>)`, never blank. With no user-facing surface, "the recording" means an e2e run plus its logs posted on the PR (API: request and server-log evidence; docs or skill text: the repo's validation run and output); say so in the report. With no e2e harness, it is a manual invocation of the changed path (script, job, or config load) plus logs. Every other gate still applies.

1. Implement and open the PR.
   - Search for an existing PR covering the change first. Follow the repo's `AGENTS.md` and the skills its rules point at; run its verification command. Minimal diff; preserve response contracts and error precedence. Conventional title prefix; include everything the caller requires. Open every PR as the requester, never as a bot or CLI identity.
   - Stacks (caller asked for one, or said to stack on an open PR): a GitHub-native layer via [`gh-stack`](../gh-stack/SKILL.md) (`gh stack link`/`gh stack add`), never a hand-set base. Open each PR as the requester, then link them bottom to top. Where `gh stack submit` would open missing PRs under a bot identity, run it only once every layer has a PR, since authors can't change. Check each new PR's author; close and reopen a bot-authored one as the requester, commenting on the old one with the new link.
   - Run [`prose-pass`](../prose-pass/SKILL.md) in embedded mode over the title and body before posting, over every later PR comment, commit message, and review reply, and over any doc or user-facing string the diff adds or changes before committing it.
   - Add `## Show me`, separate from Summary and `## Visualization`: [`show-me`](../show-me/SKILL.md) inline as one or two GitHub-rendered blocks (call-tree `diff`, pseudocode, component or file tree, Mermaid) with real symbol and file names, the smallest view that makes the change legible.
   - Where the repo deploys a preview per PR, put the preview URL in the body once it exists.
2. Prove every behavior the diff adds or changes, each at every applicable layer. Proven means red-green on identical test code: in a worktree at `origin/main`, `git checkout <head> -- <test paths>` and run there; a changed-behavior assertion fails on base and passes on head, and an unchanged-input case passes on both. Red is a failing assertion, never a missing file, import error, or setup crash.
   - **Unit**: the defect or new case, edge and error cases, and unchanged-input equivalence, per the repo's test conventions. A state machine (a `kind` union with `transition(state, event)`, or a reducer standing in for it; `transition` means that entry point whatever its name) gets a table test over every (state, event) pair, rejected pairs included, plus a fast-check property test (`fc.assert(fc.property(...), { seed: 1337, numRuns: 100 })`) driving random event sequences through the real `transition` and asserting the promised rules. When `transition` exists on both branches, both tests run on base and head; if head's tests import a runtime value base lacks (new event constructor or enum member), split them so unchanged-input cases import nothing new and run on both, and record new-value cases as head-only. When `transition` is new on head (flag-to-union migration), both tests are head-only coverage, recorded as such, and the red-green assertion goes through the public boundary both branches share (the hook, component, or route that owned the flags).
   - **Integration**: the behavior across its real boundaries (route to handler to database, service binding, Durable Object, queue) with the real local dependency.
   - **E2E**: a committed automated test of the user-facing flow in the repo's e2e harness, in addition to the step 4 recording.
   - **Observability**: for production-facing code, run [`observability-and-instrumentation`](../observability-and-instrumentation/SKILL.md)'s _Verify the telemetry itself_ step on the local stack or a synthetic fixture, forcing each failure path once. Paste the captured lines, scrubbed for the PR's audience, into the proof matrix's Observability column (evidence, not a test assertion). A failure path whose output can't explain itself is a finding; fix it before step 3. Local proof covers emitted lines only; a new alert's delivery and the staging checks stay post-deploy items, listed as untested.

   A high-risk state machine is also model-checked with [`statechart`](../statechart/SKILL.md): a TLA+ spec of the new behavior with the promised rules as INVARIANTs. High-risk means it governs money (credits, billing, caps, refunds), auth (keys, entitlements, capabilities), a request lifecycle, concurrent or retried work (queues, workflows, locks), or data deletion and retention; domain beats surface, so a payment form or deletion wizard counts. A presentation-only lifecycle (modal, form, fetch phases, wizard steps) stops at the table and property tests. The model enters no proof-matrix row; it checks the spec, not a branch.
   - Replay a model counterexample against real code first, per the `statechart` handoff: against `transition` for a single-actor path, against the concurrent boundary (Durable Object, queue consumer, workflow) for an interleaving. If neither reproduces it, the spec is wrong: fix the model before the code.
   - A reproduced counterexample, or any fast-check counterexample, is a code defect. A single-actor path becomes a table-test row; an interleaving becomes a deterministic integration test scheduling the actors in counterexample order through the real boundary, in the Integration row. Fix the code and re-run the model and new test before step 3.
   - If the defect is what the change set out to fix, that row is the red-green assertion. If head introduced it, the row is regression coverage that passes on head, with the pass-on-both check on the row itself when `transition` exists on base, otherwise through the shared public boundary.
   - A single-actor rule added to the property test or the model is added to both; an interleaving rule lives in the model and the Integration test.
   - Keep `chart.mmd` and its checked rules for step 6. A passing model over the `statechart` chart budget writes no `chart.mmd`: reduce it per that skill, and if reducing drops a relevant case, keep the TLC report for step 6's fallback.

   Use the local stack (local databases, local workers, the repo's documented dev environment), never a mock, fake, or remote environment for a dependency that runs locally; production or preview proof counts only for a surface that can't run locally, with the reason in the PR. Apply [`principle-test-behavior-not-implementation`](../principle-test-behavior-not-implementation/SKILL.md) to every test you add or change. Never edit an existing test to make new behavior pass; a test that must change is a behavior change explained in the PR. Record `## Proof matrix`: one row per behavior, a column per layer, each cell naming test file and name, the command, and the base failure (expected vs. received) beside the head pass.

3. Run the repo's [`thermo-nuclear-code-quality-review`](../thermo-nuclear-code-quality-review/SKILL.md) on the diff, driven by [`thermo-fix-loop`](../thermo-fix-loop/SKILL.md): fix, push, re-run on the new head until a pass yields no finding not fixed or refuted in writing on the PR. Actionable means a structural problem the diff introduced, fixable within its scope; record and skip anything that would grow the PR, cross an architectural layer, or need product judgment. Stop after round 4 even with findings left, and say so. Record `## Thermo-nuclear fix loop`, one block per round, the last round's empty result visible.
4. As soon as thermo is clean, record e2e video proof without waiting on review, CI, or any async gate, with the repo's e2e skill or test environment: the new behavior working plus at least one adjacent pre-existing flow the diff could break, with each test start and assertion marked where the recorder supports it.
5. A recording showing an error, stuck state, or broken layout is a finding: fix, push, re-record from scratch. A substantive fix returns to step 3.
6. Visualize every change in one self-contained `<change-slug>-<date>.html` that makes the defect and fix legible without the diff.
   - Content per `show-me`; look per [`code-diagram-html`](../code-diagram-html/SKILL.md), starting from that skill's template and passing its checks before rendering or attaching. Inline CSS and SVG only, one page, readable on desktop and mobile.
   - Pick the fitting spine (sequence, flow, decision tree, before/after, state machine), not before/after by default. Replacing lifecycle flags or a status field with a discriminated union, reducer, or transition function gets the state-machine spine: old and new state graphs side by side, states as nodes, transitions as labeled edges, old impossible flag combinations struck out.
   - In `## Show me`, the new machine goes in as a `mermaid` `stateDiagram-v2` block. High-risk: step 2's `chart.mmd` (reader-facing state labels) plus its checked rules; if the model stayed over budget, the table-drawn diagram below with a `note` reading `unchecked: drawn from the table test`, plus the TLC-checked invariants as a separate list. Other machines: drawn from the step 2 table test, one arrow per accepted (state, event) pair, plus the rules the property test asserts. Either way a `note` names the newly unrepresentable combinations and the transitions that became no-ops. The old machine appears only in the artifact.
   - The artifact holds the spine, measured numbers with iteration count for performance-shaped changes, the deciding tests and thermo rounds, and the PR's evidence links. Every number, chart, and label in it comes from this run's captured output.
   - Send it to the caller and put its uploaded URL in the PR body. GitHub strips HTML and SVG, so rasterize at device scale 2, split into as many PNGs as keep each section legible, and embed their uploaded URLs in `## Visualization`, directly after `## Show me` and before `## Before / after`. Commit neither the artifact nor any PNG. With no renderer or image host, link the HTML and name the limitation in the report.
7. For any user-facing surface, run [`before-after-ss`](../before-after-ss/SKILL.md) and put its output in the PR body as `## Before / after` below `## Visualization`. Skip only with no user-facing surface, and say so in the report.
8. Post the recording and key screenshots as one PR comment with uploaded URLs embedded, stating which flow each clip proves. Send the caller the PR link and recording now, before review is requested.
9. Run the Sol correctness loop ([`sol-loop`](../sol-loop/SKILL.md)) on the final diff of every PR, after thermo and the step 8 handoff, before the review request. Push each agreed fix and name the new head before the next round; continue the same Sol reviewer until `APPROVE` on the current head or a nit-only round (declined nits in the ledger). A behavior-changing push after approval needs another round. On budget end or a disputed item, ask the caller per that skill's stop step and change behavior only after their decision. A behavior-changing fix re-runs the affected proof and recording, and the new recording replaces the step 8 comment and caller message. Record the ledger, the Sol reviewer's link and the model that ran under `## Sol review loop`.
10. For a refactor, move, or migration (purely mechanical: yes), run [`equivalence-review`](../equivalence-review/SKILL.md) once Sol is clean. Each unintended change is a finding: fix it and redo the gates it touches. Proceed only at `✅ Pass`, proving every `⚠️` row; an unprovable row stops the gates and goes to step 15 as an open blocker with the evidence it needs. Record `## Equivalence` and re-run it whenever the head changes after passing (CI or review fix, rebase or base merge).
11. Once steps 1–10 are done, request the repository's required review with [`review-loop`](../review-loop/SKILL.md): the reviewer or review bot the caller named or the repo's rules require, through its normal mechanism, one request, whatever CI's state (pending, failing, or infra-blocked). Record the request time and return as soon as the request is sent; poll for the verdict alongside step 12.
12. While review runs, get CI green and threads resolved with the available GitHub tools and the repo's review-thread skill when it has one. If CI stays blocked, keep the review loop going and report the CI blocker separately.
13. Handle review comments yourself: fix or refute, push, reply on the thread, record a fresh request time and re-request in the same conversation, until approval. Never re-request after approval; a rebase or base merge needs no re-approval unless the repo dismisses stale approvals.
14. After approval, green CI, and all threads resolved, run [`merge-risk`](../merge-risk/SKILL.md) on the final head and append its output verbatim as the PR body's last section, `## Merge risk`, replacing any earlier one; `prose-pass` leaves it as is. Any later push re-runs it.
15. Check the checklist against the live PR's current head, required evidence sections, artifact links, CI, approvals and unresolved threads before reporting completion. Report the PR link, approval state, CI state, merge-risk level, artifact URL, and recording, naming anything untested and why. A should-fix, follow-up, "before X", or "not modeled" item you could do yourself, inside the scope the caller gave, is unfinished work, not a report line: do it first. This overrides step 3's PR-growth skips and declined nits; an item that needs product judgment or outlasted a review budget is a question to the caller, never a deferral you decide. Step 2's over-budget model fallback is a stated outcome, not a "not modeled" item, when reducing would drop a relevant case. If a caller owns the final report, hand it these facts instead of ending the session.

## Done means

On the final head:

- The repository's required approvals current, CI green, no unresolved thread.
- The PR carries every applicable step's output, current for that head: `## Show me`, `## Proof matrix`, `## Thermo-nuclear fix loop`, `## Visualization` with the artifact URL, `## Before / after`, the recording comment, `## Sol review loop`, `## Equivalence`, the preview URL, and `## Merge risk` last.
- The recording's head matches the final head in the behavior it covers, all assertions passing.
- The report carries the PR link and recording URL.

## Forbidden

- Handing the PR to a babysitter session (it pushes behind you), or any review child session besides step 9's Sol.
- `<details>` or any collapsible element in the PR body, comments, or chat messages.
- Merging.
